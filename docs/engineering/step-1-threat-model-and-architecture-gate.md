# Step 1 threat model and architecture gate

**Status:** evidence review for the engineering spikes merged through PR 10. This
is a planning decision, not a security assessment, audit, or release approval.

## Decision in brief

Proceed to a bounded design and local-only credential-storage spike. Keep the
native iOS and Android clients with a shared Rust domain core and UniFFI
boundary. Before implementing persistence, approve a separate key hierarchy
and lifecycle design that addresses device loss and migration. Do not use the
current P-256 signing keys or the PR 10 test envelope as a credential-vault
design.

This gate does not authorize production credentials, synchronization, hosted
infrastructure, app-store distribution, or a security claim. The current work
requires no hosted service, so the recurring infrastructure cost for this next
local-only stage can remain zero.

The decision is recorded in [ADR 0002](../decisions/0002-local-vault-design-gate.md).

## Evidence reviewed

The engineering sequence is complete for its stated spike questions. Public PR
numbers are not the same as the internal step numbers: internal PR 05 is public
PR 9, and internal PR 06 is public PR 10.

| Evidence | What it establishes | What it does not establish |
| --- | --- | --- |
| [PR 1: native clients and Rust bridge](https://github.com/getsotto/sotto-authenticator/pull/1) | Native iOS and Android shells call the shared Rust library through generated bindings; clean build and binding-generation steps are recorded. | Production suitability of the bridge, credential handling, or the JNA packaging/licensing decision. |
| [PR 2: TOTP core](https://github.com/getsotto/sotto-authenticator/pull/2) | Deterministic Rust TOTP behavior matches RFC 6238 vectors for SHA-1, SHA-256, and SHA-512. | Enrollment, clock behavior, persistence, or real-account security. |
| [PR 3: native TOTP integration](https://github.com/getsotto/sotto-authenticator/pull/3) | The Android UI invokes Rust for a fixed public test vector; invalid synthetic input is rejected without logging the test strings. | User seed entry, iOS TOTP UI parity, secret lifetime in production, or complete diagnostic-channel controls. |
| [PR 4: iOS protected key](https://github.com/getsotto/sotto-authenticator/pull/4) | A physical iPhone running iOS 27.2.1 created a Secure Enclave P-256 key and completed Face ID and passcode-fallback signing; an unsuccessful attempt produced no signature; cleanup was reported. | Production data encryption, passcode/biometric-change lifecycle, explicit Cancel behavior, or protection against a compromised app/OS. |
| [PR 9: Android protected key](https://github.com/getsotto/sotto-authenticator/pull/9) | On an API 37 Android 17 emulator, Keystore gated synthetic P-256 signing for biometric and configured device-credential flows; no-prompt operations were rejected outside the short authorization window. | Physical-device or hardware-backed behavior. Both keys reported software backing; API 26–36 and biometric-enrollment changes were not tested. |
| [PR 10: encrypted snapshot interoperability](https://github.com/getsotto/sotto-authenticator/pull/10) | Rust implements a temporary AES-256-GCM envelope; tests exercise failure cases; runtime-generated envelopes crossed the Swift and Android bindings in both directions. | Protected key handoff, secure key distribution, real data, portable backup, recovery, or a production file format. The fixture key and nonce are public. |

Review feedback changed evidence and implementation during these PRs. In
particular, PR 1 restricted Android ABIs to those with Rust libraries, PR 2
added a real padded Base32 test, PR 3 corrected APK packaging guidance, PR 4
fixed stale Keychain state and build issues, PR 9 corrected stale result
documentation, and PR 10 added runtime producer/consumer exchange after review
identified that a shared golden vector alone did not prove runtime exchange.
The PR descriptions and merged code record the final results.

## Assets and trust boundaries

| Asset | Current state | Required protection when real credentials are introduced |
| --- | --- | --- |
| TOTP seed | Only fixed public RFC test data is used by the apps. | Confidentiality at rest; tightly scoped access in memory; never log, include in crash reports, clipboard, screenshots, or analytics. |
| Project, instance, issuer, and account labels | No user account model or persistence exists. | Treat as private metadata: labels can reveal employer, environment, or service use even when seeds are encrypted. |
| Current and future TOTP values | Current UI shows only a known test code. | Avoid persistence and diagnostic capture; define screen capture, app-switcher redaction, and accessibility exposure behavior. |
| Device-bound private keys | Synthetic P-256 signing keys only; generated by OS facilities. | Define creation, authentication policy, invalidation, replacement, cleanup, and recovery. Never infer data-encryption capability from a signing proof. |
| Encrypted snapshot bytes | Temporary synthetic format with public key/nonce fixture. | Define authenticated versioning, unique nonce handling, key distribution, rollback policy, metadata exposure, import limits, and compatibility before use. |
| Build and signing materials | Native toolchains, generated bindings, dependencies, and developer signing are part of the build path. | Protect release signing credentials; pin/review dependencies and generators; verify generated artifacts and reproducible build outputs. No supply-chain audit has occurred. |

Trust boundaries to retain in the production design:

1. Native UI and platform process ↔ Rust through UniFFI. Values cross this
   boundary as arguments/results, so Rust zeroization cannot erase copies in
   Swift/Kotlin strings, bridge buffers, UI state, allocator storage, or logs.
2. App process ↔ iOS Keychain/Secure Enclave or Android Keystore. OS-protected
   key operations do not make an unlocked or compromised app trustworthy.
3. App-private filesystem ↔ OS backup, device restore, export, and migration.
   The current spikes define no backup exclusion or restore behavior.
4. One device/platform ↔ another through user-controlled export/import or a
   future service. PR 10 crossed test bindings with public fixture material;
   it did not cross a protected key boundary.
5. Source and build inputs ↔ release artifacts. UniFFI/JNA, Rust crates,
   Gradle/Maven, Swift/Xcode tooling, CI, and signing identities all enter the
   software supply chain.
6. App ↔ any future remote service or object storage. No such service exists
   in this stage, so its authentication, authorization, encryption, tenancy,
   backup, and operations are all undecided.

## Attacker paths and residual risks

| Scenario | Evidence and current mitigation | Residual risk / decision needed |
| --- | --- | --- |
| Lost or stolen, locked device | iOS test key used `WhenPasscodeSetThisDeviceOnly` and `userPresence`; Android emulator Keystore rejected unauthenticated operations in recorded probes. | No real vault exists. Android physical-device strength is unknown. Define device lock, app unlock, retry, and credential invalidation policy. |
| Lost or stolen, unlocked device | None of the spikes tested a real account vault. | A person with an unlocked device may access an open app or active authorization window. Define auto-lock, foreground behavior, reauthentication and exposure limits. |
| Attacker knows device passcode | iOS passcode fallback succeeded; Android device PIN fallback succeeded under its five-second authorization policy on the emulator. | Passcode fallback is a usability choice, not a defense against an attacker who knows the passcode. Decide whether to support it and for what operations/window. |
| Malicious or compromised app / OS | OS key stores gate access to protected key operations in the synthetic experiments. | A compromised process can request permitted operations, capture plaintext after decryption, or alter displayed codes. Platform key protection does not solve runtime compromise. |
| FFI, allocator, and language-runtime copies | TOTP zeroization is best-effort inside Rust; docs explicitly acknowledge caller/FFI/implementation copies. | Swift/Kotlin and bridge copies can outlive the Rust buffer. Design narrow APIs and short lifetimes; characterize whether mutable byte buffers can avoid immutable string copies. |
| Logs, crash reports, screenshots, clipboard, accessibility | Existing UI uses fixed public fixtures and review scanned selected logs; the iOS harness does not display key/challenge/signature. | There is no production-path evidence for any channel. Specify and test redaction, capture prevention/response, clipboard policy, accessibility, logging, and crash-report scrubbing before real seeds. |
| Passcode, biometric, or lock-state changes | iOS passcode/biometric lifecycle changes remain untested. Android emulator lock removal invalidated the alias; PIN change had an immediate successful operation before later denial. | Lifecycle behavior varies by policy and device. Define invalidation/re-enrollment and recovery behavior; test supported physical devices. |
| Backup/restore, device migration, or loss | Apple’s device-only Keychain class is documented not to migrate; Android Keystore experiment keys are app/device-bound in practice. | A device-bound key alone strands data after loss or reinstall. Decide a portable recovery mechanism before choosing persisted encryption. |
| Malformed, modified, replayed, or oversized import | PR 10 rejects malformed headers, invalid tags, unsupported fields/versions, and oversized payloads in synthetic tests. | No production schema, rollback detection, canonicalization, metadata privacy, or operational migration exists. Add those to a separately versioned format design. |
| Future server or object-storage compromise | No server, object storage, analytics, or network sync is present in the current implementation. | This evidence says nothing about a future service. Keep backend and service cost out of the next stage; if introduced, require a new threat model and service-specific review. |
| Dependency, build, or signing compromise | PRs record locked Rust builds, generated binding checks, and selected leak scans. | This is not a supply-chain assessment. Establish dependency review/update policy, CI provenance, signing-key custody, release permissions, and artifact verification before release. |

## Architecture recommendation

### Retain these boundaries

- Keep iOS and Android clients native, with UI, lifecycle, secure storage, and
  system authentication in platform adapters.
- Keep shared TOTP/domain behavior in Rust behind generated UniFFI bindings.
- Keep the Rust core independent from platform key-store APIs. Platform
  adapters should request the minimum operation needed and pass only the
  minimum necessary plaintext into the core.
- Keep the service absent from the next stage. A local-only persistence design
  has no recurring infrastructure requirement and matches the near-zero
  initial-cost constraint.

### Do not promote spike keys or envelopes

The iOS and Android keys prove authentication-gated P-256 signing. They are not
AES keys, and PR 10 did not wrap or use them. Do not derive or relabel those
keys as a vault key. The PR 10 envelope has a deterministic public test key and
nonce; its format, nonce handling, payload schema, and key distribution are
not approved for user data.

### Design gate before persistence

The next design must compare, at minimum:

1. A random local vault key protected by each platform's native key storage,
   plus a separate portable export/recovery mechanism.
2. User-controlled recovery material that can unlock an encrypted export on a
   new device, with explicit consequences for forgotten recovery material.
3. Whether importing/exporting is a separate user-driven operation or a later
   optional service. Do not assume OS key synchronization is cross-platform
   migration.

For each option, specify key generation, wrapping, unlock policy, passcode and
biometric changes, lockout/invalidation, loss/reinstall, deletion, export,
restore, versioning, nonce management, and memory/diagnostic exposure. Measure
physical Android key security levels and the supported iOS keychain behavior.
Do not select a key derivation or recovery scheme solely from this spike.

## Cost and operations boundary

The next local-only prototype can continue to run without a backend, account
service, object storage, email, or paid API. Its recurring infrastructure cost
is therefore zero, excluding developer time, test hardware, and any existing
developer program costs. This is a scope observation, not a forecast for a
future sync service. Any hosted sync, recovery, or account feature requires a
separate architecture and cost decision before implementation.

## Required follow-up and owners

| Owner | Next evidence or decision | Gate |
| --- | --- | --- |
| Product and maintainers | Define recovery expectations for device loss, forgotten recovery material, and multi-device migration; confirm whether sync is out of scope for the first vault. | Before key hierarchy ADR. |
| iOS maintainer | Characterize Keychain-protected symmetric-key storage, access control, passcode removal/change, backup/restore, backgrounding, and deletion on supported iOS versions. | Before iOS persistence implementation. |
| Android maintainer | Characterize AES-GCM Keystore key use, authentication window, invalidation, backup/restore, key security level, and behavior across representative physical devices/API levels. | Before Android persistence implementation. |
| Core maintainer | Propose narrow Rust/FFI interfaces for TOTP and encrypted payload handling; document string/buffer copies, limits, errors, zeroization boundaries, and format versioning. | Before accepting real seeds into the Rust API. |
| Release/build maintainer | Review JNA packaging/licensing, dependency update policy, CI provenance, generated bindings, and signing-key handling. | Before any release candidate. |
| Maintainers / independent reviewer | Decide whether an external security review is needed and define its scope and timing. | Before production release; not required to run the bounded design spike. |

## Explicitly out of scope

No production credential vault, QR or migration import, recovery kit, cloud
sync, server protocol, object storage, account service, remote deletion,
operational restore, app-store release, independent audit, or claim about the
security of the inherited Sotto core is approved by this decision.
